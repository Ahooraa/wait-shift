# Specification of the Heu and RL baselines (PLAN.md phases 6-7)

Same rules as PLAN.md section 0: use each source paper's own published settings unchanged, same simulator/workloads/seeds/capacities
for every method, implement line by line, errata and adaptations are labelled, nothing is tuned toward a result. Sources were read
twice (text layer + rendered pages) and are quoted by section/equation.

## How DFPS used the two baselines (the only authority on the intended adaptation)
DFPS paper p.9 Sec.5.1: *Heu* [18]: "a state-of-the-art heuristic ... similarities with DFPS in terms of the application model,
network infrastructure, and placement and scheduling strategies. Unlike the proposed algorithm, however, Heu performs function
placement and scheduling **simultaneously for each function request**" (no initial placement). *RL* [28]: "a recent RL-based algorithm".
DFPS p.10-11 (results text): Heu and RL "do not rely on an initial placement. Instead, they make placement and scheduling decisions
individually for each incoming request ... frequent replacement increases the number of cold starts"; RL "lack of awareness of workflow
structure during scheduling. Tasks are scheduled independently, leading to their distribution across multiple edge nodes ... more cold
starts and increased data transmission delays"; Heu has low utilization (cold starts, little reuse); RL has high utilization from "the
aggressive removal of idle instances to accommodate incoming ready requests".
The DFPS paper does not describe any further adaptation. Everything below that is not in a source paper is an assumption (AB-xx).

## 1. Heu: Xu, Zhou, Liang, Xia, Xu, Ren, Ren, Zhou, "Stateful serverless application placement in MEC with function and state dependencies", IEEE Trans. Computers 72(9):2701-2716, 2023 (DOI 10.1109/TC.2023.3262947)

### 1.1 Verified content (Sec.3-4.1, Alg.1)
- **Model [Sec.3.1-3.5]:** MEC network G = (CL, E): cloudlets CL_i with memory capacity M(CL_i); links with unit delay d_e and cost c_e.
  Application F = DAG G_f = (V_f, E_f) of functions f_l, each invoked N_l times per request; request r_j has data volume rho_j and a source node v_j;
  state a_{l,j} = rho_j * eta_l generated by f_l and possibly needed by non-successor functions (state dependency).
- **Processing delay (Eq.1):** d^proc_{l,j}(CL_i) = (x_{j,l,i} + x'_{j,l,i}) * alpha_i * M_i * N_l * rho_j + x_{j,l,i} * d^o_{l,i}
  (x: newly instantiated container, x': existing container, d^o: cold-start delay; alpha_i: memory-allocation influence factor; M_i: memory per unit data).
  Request delay d_j (Eq.3) = max over execution paths of processing + state/data transmission ((rho_j + a_{l,j}) * d_e per link).
  Costs (Eq.4-7): processing sum (x+x') rho_j M_i D_i c_l N_l; transmission (rho_j + a_{l,j}) c_e; storage a_{l,j} c_i; c_j = sum.
- **Problems:** P1 min sum_j c_j s.t. d_j <= d_j^req and memory capacity (Eq.8-16); P2 min sum_j (xi*c_j + (1-xi)*d_j) (Eq.17). Both NP-hard.
- **Heuristic "Heu" (Sec.4.1, Alg.1), four stages:**
  1. *State-placing DAG* G'_f: add a virtual state node n_l per function that generates state, edge <f_l, n_l>, and <n_l, f_l'> for each original edge <f_l, f_l'>.
  2. *Parallel schedule*: topological sort of G'_f into sequential partition components A_{F,q} of independent functions; the functions of a component are consolidated into one cloudlet.
  3. *Auxiliary graph* G'(F): |A_F| layers; per cloudlet two virtual nodes CL_{i,q} -> CL'_{i,q}, edge capacity M(CL_i), edge cost
     sum_{f in A_{F,q}} (M_i D_i c_l N_l) + sum_{f^s in A_{F,q-1}} (c_i eta_l) (Eq.18/19), edge delay max_{f in A_{F,q}} (alpha_i M_i N_l + d^o_{l,i}) (conservative: cold start assumed);
     network edges in layer q get cost/delay c_e (1+eta_l), d_e (1+eta_l) summed over states of A_{F,q-1}; zero-cost links CL'_{i,q} -> CL_{i,q+1}; source v_j -> every CL_{i,1}; common sink u_F.
  4. *Assign requests*: sort requests by non-decreasing data volume; for each: prune edges whose memory demand can not be met, find a **delay-constrained shortest path** from v_j to u_F, create an instance of each function (or virtual state node) of partition component A_{F,q} in cloudlet CL_i for every edge <CL'_{i,q}, CL_{i,q+1}> on the path, update residual memory; repeat.
- Alg.1 lines 1-9 read; the tail of Alg.1 (what happens after instance creation: residual capacity update, request admission/rejection) and Sec.6.1 parameters are to be read once more before coding.

### 1.2 Adaptation questions (must be decided and logged before coding)
| ID | Question | Why it matters | Proposed neutral default |
|---|---|---|---|
| AB-H1 | Heu's resource is **cloudlet memory** with a continuous demand `M_i * rho_j` per request; DFPS's resource is **container slots** `ecc_k`. | Different capacity model. | Map "memory demand of a function instance" to **one container slot** per instance; M(CL_i) = ecc_k. |
| AB-H2 | Heu optimises **cost** (P1) / weighted cost+delay (P2); DFPS measures **makespan**. | The shortest path uses edge costs. | Run Heu as published (P1 cost weights from Eq.18/19 with the delay constraint); report its makespan. A delay-only variant is an extra, labelled experiment. |
| AB-H3 | Per-request data volume `rho_j`, `eta_l`, `alpha_i`, `M_i`, `D_i`, `c_l`, `c_e`, `d_e`, `c_i`, delay requirement `d^req_j` are not defined by the DFPS workload. | Needed to build edge weights. | Derive from DFPS quantities: `rho_j` = input state size; `eta_l` = SS/rho; `d_e` = h/bw from Eq.1-2; costs proportional to run-time; `d^req_j` = none or generous (documented). |
| AB-H4 | Heu is an **offline batch algorithm** (sort all requests by data volume), DFPS needs an online system. | Ordering. | Apply Stage 4 **per arriving request** (online); Stages 1-3 once per workflow type. (Matches DFPS's "simultaneously for each request".) |
| AB-H5 | DFPS tasks: one container per task invocation. Heu consolidates a partition component's functions into **one cloudlet** and creates a **new instance per request**. | Defines Heu's cold starts. | Follow Heu: new instance for every function of every request (cold start `d^o`), released after use; existing idle instances are reused only if Heu's text says so (check Eq.1: x' = existing container). |
| AB-H6 | State nodes: Heu places states in cloudlets (virtual state nodes). DFPS stores output states on the nodes of the child tasks. | State placement. | Use Heu's virtual state nodes with the DFPS storage limit `esc_k`. |

## 2. RL: Yang, Du, Ye, Ding, Wang, Chen, Li, "Multi-objective deep reinforcement learning for function offloading in serverless edge computing" (MOSEC), IEEE Trans. Services Computing 18(1):288-301, 2025

### 2.1 Verified content (Sec.III-V)
- **Model [Sec.III]:** one cloud server X_0 (all functions deployed, unrestricted memory) + M edge servers (subset of functions deployed); a user device (UD) sends requests over wireless links.
  Application = DAG of functions v_i = <d_i (input), q_i (output), mem_i, cw_i (CPU cycles)>. Containers on edge servers have three states: occupied, idle (no-load for a period, ready to run the next function) and
  available (recycled resources that must cold-start, T_c). Execution time T_i^e (Eq.6) = T_c + cw_i * omega_m (no idle container, resources available), cw_i * omega_m (cloud, or idle container), infinity otherwise.
  Completion time T (Eq.2-10): input transmission (UD->edge: d_i / r_w, r_w = B_w log2(1+SNR); UD->cloud: fixed t_ec), predecessor transmission (edge-edge q_j / r_e; via cloud t_ec), earliest start ST_i = max finish of predecessors, T = max FT over exit functions.
  Energy (Eq.11-13) and cost (Eq.14-18, AWS-Lambda-style, memory rounded to 64 MB steps in [128, 3008]).
- **MOMDP [Sec.IV-A]:** 6-tuple <S, A, P, r, Omega, f>; **state** s_t = (u_t = features of the function to offload, g_t = channel conditions UD-servers, c_t = computing capacity of servers); **action** a_t in {0..M} = execution location (0 = cloud);
  **reward** vector r_t = (r^T_t, r^E_t, r^C_t) with r^T_t = T(U_{t-1}) - T(U_t) (negative increment of completion time after placing the t-th function of a priority sequence U), r^E_t = -E_t, r^C_t = -C_t; scalarisation f(V, w) = w . V.
- **Algorithm [Alg.1 NER sampling, Alg.2 learning]:** DDQN; per episode a random preference vector w_k; epsilon-greedy action; buffer B of (s, w, a, r, s'); **NER** sample: draw lambda*b transitions, score each by ||s_k - s_t||_2 + ||w_k - w_t||_2, keep the b with the highest similarity (Alg.1 sorts "ascending" and takes the first b = smallest distance); **EF** scheme: pick the earliest history-trained preference vector from the encountered set; loss = 1/2 [mse(y^k, Q^k) + mse(y^h, Q^h)] (Alg.2 l.19; Eq.20-22 write the loss with absolute values, see AB-R6); target network synchronised "each N-step" (Alg.2 l.22) vs "every N-episode" (text): inconsistent.
- **Published settings [Sec.V-A]:** 1 cloud + 6 edge servers; edge CPU 1-3 GHz, cloud 3 GHz; cold start 1 s; DDQN: two identical networks, **2 hidden layers x 64 neurons, Tanh, Adam lr 0.001, gamma 0.99, replay buffer 5000, batch 64, NER lambda = 3**.
  Test apps App-1..6 with 10/10/20/20/30/30 functions (input 500-600 KB, output 50-100 KB, 1-5 Gcycles, 64-512 MB).

## 3. Common tests (before any result is reported)
- Constants/units: every number quoted above equals the paper's (two-source check recorded in the code comments).
- Heu: toy instances where the auxiliary-graph shortest path equals brute force; memory-pruning test; per-request new instances create cold starts; same DFPS metrics pipeline.
- RL: DDQN update unit tests (target computation, NER ordering, EF choice); it must beat a random policy on a training workload, and be evaluated only on separate test seeds; a learning curve is saved.
- Both: run in the same simulator with `check_invariants`, identical workloads/seeds.

## 5. Decisions taken (2026-10-13; the user asked for "the best standard approach acceptable by top journals")
Adopted: every default proposed in sections 1.2 and 2.3, plus the following, which are what a reviewer expects of a re-implemented baseline:
1. **Published settings unchanged.** MOSEC: 2x64 Tanh, Adam 1e-3, gamma 0.99, buffer 5000, batch 64, NER lambda 3. Heu: Alg.1 structure, Eq.18-19 weights, conservative delay.
2. **Same simulator, scenario, seeds, capacities, execution-time draws and metrics** for SR, SG, DFPS, Heu and RL (`dfps/ondemand.py` for the two on-demand baselines).
3. **Common on-demand container model (AB-C1..C4)**, identical for Heu and RL so that only the node-selection rule differs: slots start empty; warm container of the function, else free slot (cold start), else recycle the LRU idle container of another function (cold start), else FIFO wait. No idle time-out, because neither DFPS nor the baselines specify one.
4. **AB-H7**: Heu's source edge v_j -> CL_{i,1} carries the real transfer of the request input (v_j is a network node); Heu is run per arriving workflow (online), pruning uses residual slots (capacity - occupied - queued) and free storage; a component larger than a node runs in waves. Delay requirement d_req = 2 x least achievable delay of Heu's conservative model (AB-H3). Because DFPS has no per-node cost/delay coefficients, Heu's path cost reduces to hops x MB; this is stated in the paper's results as a property of the model, not hidden.
5. **RL training protocol**: trained once, offline, on 24 training workloads (seeds >= 1000; Uniform and Pareto; scale 0.5-2.0; 90 s each), evaluated greedily (epsilon 0) on the test seeds 1..N. The learning curve is saved (`results/rl_policy.json`). The free parameters of AB-R5 were fixed before any test run and are NOT tuned on test seeds.
6. **Reporting rules**: report all methods on the same workloads with repeated-measures ANOVA (Sec.5.2 of DFPS), state which numbers come from re-implementation, publish code/config/seeds, and run a sensitivity study of every non-published baseline parameter (Heu delay slack; RL epsilon schedule, training length, reward scale).
7. **Still unavailable**: MOSEC Appendix A/B (network layout and learning details). Documented as a limitation; our per-node scoring network is the stated substitute.
