Four errors in the printed DFPS method, and how B* fixes them

E1Eq. 3 · page 6placement cost

The placement cost always comes out as zero

What the paper prints

Eq. 3 measures how far a placement is from the ideal one. For every function fl it compares how many containers the function actually has (FAN) with how many it should have (FEN), and adds up the differences with a plain sign, without an absolute value.

Σfl ∈ F ( FAN(fl) − FEN(fl) )   ← printed: no |…|

Why it breaks

Both counts share out the same containers: the actual counts add up to all container slots, and Eq. 4 shares the same total out as the ideal counts (pp. 5–6). So every function with too many containers is balanced by functions with too few. Pluses and minuses cancel, and the sum is exactly 0 for every placement, good or bad. The method cannot tell placements apart.

Small example

Three functions sharing 6 container slots. The ideal is 2 / 2 / 2; the actual placement is 5 / 1 / 0, which is clearly bad.

f152+33

f302−22

Printed cost: 0, the same as a perfect placement. With absolute values: 6, so the badness is visible.

Our fix and its effect

Σfl ∈ F | FAN(fl) − FEN(fl) |

With the printed cost, the paper's SG baseline is no better than random placement. That is why the printed DFPS fails the paper's own claim "DFPS beats SG, which beats random" at 3 of 4 load scales in our reproduction. With the fix, the claim holds at all 4.

E2Eq. 6 · page 7queue length estimate

The queueing formula mixes up time and rate, and misses a term

What the paper prints

Eq. 6 estimates the number of requests for function fl on node ek, which has fnlk containers and receives λlk requests per second:

FRN(fl, ek) = (λlk/μl)fnlk λlk μl / [ (fnlk − 1)! (fnlkμl − λlk)2 ] + λlk/μl

The textbook formula for the same quantity (M/M/c queue, c containers) is

L = P0 · (λ/μ)c λ μ / [ (c − 1)! (cμ − λ)2 ] + λ/μ,   μ = service rate

So the printed formula is the textbook one with P0 left out. Four things go wrong:

  • Time used as a rate. The paper defines μ as the average execution time (p. 7), and Eq. 4 uses it as a time. In λ/μ and nμ − λ it only makes sense as a rate (requests per second).
  • Missing P0. The real Erlang-C formula needs P0, the probability that the system is empty. Without it, the size of the result is wrong.
  • Wrong label. The formula adds λ/μ (requests being served), so it counts requests in the whole system. The text calls it "requests in the queue".
  • No overload check. When requests arrive faster than containers can serve them (λ ≥ nμ), no finite queue length exists, but the formula still returns a number.

Small example

A function takes 0.5 s per request and has 2 containers. Requests arrive at 3 per second. Each container can serve 1 / 0.5 = 2 requests per second, so together they handle 4 per second: the system is busy (75%) but stable.

Plug in μ = 0.5 (the time, as printed)
nμ − λ = 2 × 0.5 − 3 = −2

A negative capacity margin: the formula says the system is overloaded and gives a meaningless (negative) queue, although it is fine.

Use μ = 1 / 0.5 = 2 per second (a rate)
nμ − λ = 2 × 2 − 3 = +1

Full Erlang-C with P0 = 1/7: on average 1.93 requests wait in the queue, and each waits about 0.64 s.

Erlang-C with P0 (our fix): waiting time for this example as arrivals increasecapacity limit: 4 requests per second

The correct curve stays small at low load and shoots up as arrivals approach capacity. Beyond capacity there is no steady queue, so we treat that case explicitly.

Our fix and its effect

  • Use the service rate μ = 1 / execution time
  • Use the standard Erlang-C formula including P0 (computed in a numerically stable way)
  • Label the result correctly and handle overload (λ ≥ nμ) explicitly

This estimate decides where requests are sent and how the annealing scores a placement. With the wrong units, busy functions can look idle and idle ones busy.

E3Algorithm 2 · page 9simulated annealing

The search keeps every bad move and returns wherever it stops

What the paper prints

Simulated annealing improves the placement step by step. Each loop makes a neighbour placement (line 5) and scores it: Δ ← EF(Solt) (line 6), where Δ < 0 means the change made things worse. The printed rule (lines 7–9): if Δ < 0, undo the change if

random(0,1) ≥ e−Δ/T   ← printed, with Δ < 0

The temperature is lowered every loop (line 12). The step counter t is set to 1 (line 3) and never increased, and the loop returns Solt, the last placement (line 14).

Why it breaks

  • If Δ is negative, then −Δ/T is positive, so e−Δ/T is greater than 1. A random number between 0 and 1 is never ≥ a number above 1. So a worse change is never undone.
  • Because t stays at 1, line 5 literally rebuilds Sol1 from Sol0 on every loop. The indices only make sense if t is increased each loop.
  • The search can end on a placement worse than one it already found, and it returns that worse one.

Example with δ = −0.5 and T = 1: the threshold is exp(0.5) ≈ 1.65. Every random number (0 to 1) falls short of it.

Toy illustration

A made-up search problem, run with the same random numbers both ways. It shows the behaviour, not DFPS's real numbers.

Our fix and its effect

keep a worse move with probability eΔ/T (between 0 and 1); continue from the current placement; return the best placement found

This is the standard Metropolis rule. It still sometimes keeps a worse move to escape local traps, but less often as the temperature falls (the paper's own line 12), and it never throws away the best placement it has seen.

E4Algorithm 1 · page 8replacing a function

Moved requests are copied into the wrong queue and never removed

What the paper prints

Algorithm 1 picks a node es, removes one instance of its least-used function fr and starts an instance of a random function fn instead (lines 2–5). If that was the last fr instance on the node, its waiting requests go to the best other node (lines 7–17). Then waiting fn requests on nearby nodes es′ are pulled over to the new instance if that helps (lines 19–25). Three things go wrong:

  • Line 23 adds the pulled-over fn request to FRQrs, the queue of fr on es. That is the queue of a different function. The new fn instance, which the request was moved for, never sees it. It should be FRQns.
  • Line 23 also never takes the request out of FRQns′ on the nearby node, so it now waits in two queues. (Line 16 has the same gap, but there the old queue belongs to the instance that was just removed, so it matters less.)
  • Line 9 sets es′ ← ∅, so the first comparison on line 12, AET(rq, es′), compares against a node that does not exist.

R7 moves: it leaves the nearby node's queue and joins the new fn instance's queue. Every request exists exactly once.

Our fix and its effect

  • Line 23: append to FRQns (the new fn instance), not FRQrs
  • Remove the request from its source queue when it moves (lines 16 and 23)
  • Give e_s′ a starting value, so the first comparison is defined

Our simulator checks that each request is in exactly one place. Followed literally, the printed lines would break that check, so they cannot be run as written.
